# CrossFlow v1 mandate contract — T02

Status: specification candidate, awaiting independent review and T04 cross-language implementation. No deployed program or security-audit claim. Normative words MUST/MUST NOT identify acceptance requirements. This freezes the funding authorization, not a selected solver trade plan: the solver may cooperatively adjust trades inside the funded raw-output bounds. Human target percentages and optimization constraints remain off-chain preferences unless reduced to the explicit checks below.

## Scope, integers and deployment domain

The release target is 2–3 distinct owners, exactly three allowlisted base SPL assets (two fixture stocks and cash), and at most two residual swaps per atomic settlement. Single-owner settlement is allowed only for a marked technical probe. Funding is one owner per transaction. No partial fills. All approved assets appear in each mandate even when funding is zero. MAX_AMOUNT = 1,000,000,000,000 raw units per intent/asset, with every funding, bound, debit, per-owner residual input and output at most this value. Asset decimals are 0–9. The total pool balance per asset must not exceed 3 × MAX_AMOUNT. Price bounds and arithmetic are specified in settlement-accounting.md.

All external JSON integer values are canonical decimal **strings**, including versions and enum values: `0` or a nonzero digit followed by digits; no sign, whitespace, exponent, fraction or leading zero. Public keys and digests in vectors are lowercase 64-character hex representing 32 bytes; user interfaces may display base58 but MUST decode before hashing. Ordinary JSON object serialization is never a signature or hash preimage. Little-endian integers have fixed widths; arithmetic is checked and rejects overflow. Unknown fields, versions, enums, extra bytes, wrong lengths, and noncanonical input are rejected, never ignored.

The network domain is the raw 32-byte decoded genesis hash; the expected devnet genesis is configured by the deployment tool. A local fixture deployment uses its verified local genesis. Program ID, config PDA and network domain are in each canonical commitment. Solana programs do not receive an RPC genesis hash from the runtime: the immutable config contains the deployment's genesis, and all signing clients MUST independently compare the RPC genesis before signing. This boundary is S01, not an on-chain claim that the program can query the network. Fixture and future authenticated Pyth modes have distinct config hashes and cannot be switched by a caller flag.

## Immutable config and policy commitment

Initialization authority is a compiled deployment constant, never the first caller. Before building the reviewed artifact, its versioned deployment manifest fixes `expected_initializer`, `expected_initial_admin`, genesis, program_id, deployment_id, derived config_address and SHA256 of the exact initial policy bytes. These public values are embedded as program constants and checked against the release manifest/source/binary identity by deployment tooling. `initialize_config` requires the expected_initializer transaction signer; requested admin must equal expected_initial_admin; all identities and initial policy hash must equal the compiled expected values, and version must be1. This permits no caller-selected admin/policy/domain or arbitrary deployment_id. Initialization is exactly once for that config and rejects any already initialized account. A random deployment_id is public domain separation, **not a secret capability**. Attacker-first initialization with the right ID but wrong signer fails before state creation. Creating another config requires a newly reviewed deployment artifact/identity, not a caller-provided alternate seed. Any redeployment/update of these constants follows the no-outstanding-claims upgrade procedure and requires fresh owner authorization for a new config. Test prefunded empty system-account PDA handling without relaxing signer/identity checks or treating a pre-existing initialized config as reusable.

Config PDA = `find_program_address([b"config", deployment_id[32]], program_id)`, where a fresh public random deployment_id is chosen once. It stores that ID, program/network identities, configuration_version, policy fields below, admin, pause bits and outstanding_claim_intents. Config address is immutable; config and owner-state accounts cannot be closed in v1, preserving old-nonce donation recovery after policy rotations. Program validates its PDA and own program ID, never accepts a caller-supplied arbitrary account with the right shape. Configuration version starts at 1; policy mutation increments it, requires admin and outstanding_claim_intents == 0, and replaces the exact config hash. Admin changes also require zero outstanding claims. Pause bits are operational fields outside the commitment; they can only disable funding/settlement. Counters are outside the commitment. Neither can disable cancellation/recovery.

`policy_hash = SHA256(policy_bytes)`; **policy_bytes**, in this exact order, is:

| Field | Encoding |
|---|---|
| domain | ASCII `CFLCFG01` (8 bytes) |
| genesis, program_id, config_address | 32 bytes each |
| configuration_version | u32 LE, nonzero |
| oracle_mode | u8: 0 fixture; 1 Pyth reserved and rejected by v1 implementation until T15/admission review |
| cash_index | u8, 0–2 |
| asset_count | u8, exactly 3 |
| assets, in strictly ascending raw mint-byte order | For each: mint[32], token_program[32], decimals u8, feed_id[32] |
| route_kind | u8: 0 disabled or 1 controlled fixed-function venue; all other values rejected |
| route_program, pool, pool_authority | 32 bytes each; all zero only for disabled route |
| route_vaults | three 32-byte addresses, corresponding to assets; all zero for disabled route |
| max_route_legs | u8, 0 if disabled, exactly 2 if enabled |
| max_age_seconds, max_future_skew_seconds | u32 LE each |
| max_confidence_bps, max_reference_move_bps, max_value_loss_bps, max_cross_deviation_bps, max_external_deviation_bps | u16 LE each |
| max_intent_lifetime_seconds | u32 LE |
| fixture_publisher | 32 bytes; nonzero fixture authority, zero for future authenticated mode |
| protocol_fee_bps | u16 LE, exactly 0 |

V1 defaults: age 60 s; future skew 2 s; confidence 100 bps; reference move 500 bps; value loss 200 bps; internal cross deviation 100 bps; external execution deviation 200 bps; lifetime 900 s. Admission validation requires age 1–60, skew 0–2, confidence 0–100, move 0–500, loss 0–200, internal cross deviation 0–100, external execution deviation 0–200 and lifetime 1–900. These are hard maxima, not thresholds a solver can widen. Fixtures may demonstrate rejection via stale/wide/moved observations without changing policies. Cash is a test token valued at exactly 1,000,000 price units per whole cash token, confidence 0; this is a fixture assumption, not a stablecoin guarantee. Test stock mint authorities must be revoked after fixture inventory is minted; freeze authorities must be absent. Asset token_program must be the canonical legacy SPL Token program; Token-2022 and unknown programs are rejected. Every token account must be initialized and unfrozen, use the exact mint, and have no delegate or close authority. Config must fix these checks; they are not a caller-provided extension hash. Fixture reset uses fresh configuration/mints if inventory needs increasing.

The controlled venue's exact ABI, fee schedule and reserve rules are frozen in T10 before routes are enabled; T16 integrates and validates the actual residual CPI. T04/T05 use route_kind=0 and no CPI. T10 must add a versioned policy extension (new schema/config version) if the existing fields do not bind every security-relevant venue parameter. It cannot treat this placeholder as a working adapter. A disabled-route config still permits internal crossing when the accounting pool can satisfy all outputs without external liquidity. The known T10/T16 boundary is independent of funding semantics.

## Funding payload and canonical mandate

A owner signs `create_and_fund` directly. There is no off-chain detached signature, wallet-message signature or solver authorization signature. The instruction is atomic: validate the exact request, move all F, initialize all state, and increment nonce/counter, or revert everything. The owner sees all resolved fields, outputs and loss settings before signing. Source balances outside this funded slice do not affect settlement bounds.

For payload capacity, the instruction carries only the compact body below. Program ID comes from invocation, owner from the signer account, genesis/config/policy/asset identities from validated config, and recipient addresses from canonical ATA derivation. The program reconstructs and stores the canonical commitment. **The compact payload includes expected_policy_hash**; mismatch aborts, so a configuration change between review and submission cannot change the signed meaning.

Compact body order (instruction discriminator is separate): schema_version u8 = 1; expected_policy_hash[32]; nonce u64 LE; expiry_unix_seconds u64 LE; optimization_commitment[32]; then for each of the three configured assets F u64 LE, min_output u64 LE, max_output u64 LE, funding_reference_price u64 LE. Body length = **177 bytes**. No dynamic array prefix is present because v1 has exactly three assets. Anchor instruction discriminator, transaction signing/message bytes, account metas and PDA creation are additional size, not included in 177. T04 MUST measure full serialized funding and settlement envelopes.

`mandate_hash = SHA256(mandate_bytes)`, exact canonical order:

| Field | Encoding |
|---|---|
| domain | ASCII `CFLINT01` (8 bytes) |
| schema_version | u8 = 1 |
| genesis, program_id, config_address, policy_hash, owner | 32 bytes each |
| nonce, expiry_unix_seconds | u64 LE each |
| optimization_commitment | 32 bytes, nonzero |
| asset_count | u8 = 3 |
| each asset in config order | mint[32], token_program[32], decimals u8, recipient_ATA[32], F u64 LE, min_output u64 LE, max_output u64 LE, funding_reference_price u64 LE |

Canonical preimage length = **605 bytes**; it is not repeated in settlement instruction data. Funding payload and canonical commitment are different representations of the same fully resolved request. No solver can substitute a policy or omit an asset by choosing the compact representation. Intent state retains owner, nonce, expiry, policy_hash, mandate_hash, optimization_commitment, F/min/max/funding_reference arrays and status. Resolve identity fields only against the matching unchanged config. If account layout changes, T04 must retain all semantics rather than quietly dropping fields.

The optimization commitment is SHA256 of a separate versioned canonical economic manifest to be frozen in T04 with T01 inputs. V1 funding treats this as an opaque nonzero 32-byte commitment and MUST display the exact manifest/hash. It does not on-chain enforce hidden constraints inside that manifest. Actual raw bounds, prices and route policy remain explicit. Browser and numerical service must not advertise opaque risk preferences as on-chain guarantees.

Recipient for each asset is exactly the owner's canonical ATA derived with seeds `[owner, token_program, mint]` under the canonical Associated Token Account program (allowing off-curve owner only when a later explicit admission policy supports it; v1 requires a transaction-signing wallet). Source account is this same ATA, validated before funding. It can also be the settlement/refund recipient: this alias is intentional. The program cannot accept an alternative recipient even with a matching token mint. Owner cannot redirect an already funded intent; cancel/refund then reauthorize instead.

Funding requires `now < expiry <= now + max_intent_lifetime_seconds`; on-chain Clock is authoritative; checked timestamp conversion rejects negative runtime clock/overflow. Require `0 <= min <= max <= MAX_AMOUNT`, `F <= MAX_AMOUNT`, at least one F > 0, and funding_reference prices matching the authenticated fixture snapshot selected for funding. Zero reference prices are invalid. Bounds may exclude F (rebalancing may be required); protocol does not promise a feasible batch. Solver feasibility is checked off-chain before presenting funding; owner recovery remains available for infeasible requests. Funding authenticates a fresh, confidence-valid snapshot using the same oracle guard as settlement. No partial or repeated top-ups.

## PDA identities, persistent nonce and lifecycle

- Owner state PDA: seeds `[b"owner", config_address, owner]`, records next_nonce u64, active_intent option and owner. New account starts next_nonce=0. It is **never closed** in v1. Funding request nonce must equal next_nonce; checked increment occurs on successful funding; u64 exhaustion rejects new funding.
- Intent PDA: `[b"intent", config_address, owner, nonce_u64_le]`. The authority over each intent vault is this PDA. Vault is the canonical ATA of intent PDA, mint, legacy token program. Verify ATA address, token owner, mint and authority, not merely account labels.
- One active claim-bearing intent per owner/config. active_intent is set during funding and cleared only on final closure after **all booked and surplus claims** are empty. Settled/cancelled but not closed blocks another funding, avoiding stranded claims and ambiguous recovery.
- Intent/counter initialization and all three funding transfers are atomic. Pre-existing vault ATAs may be reused if every identity/state check passes. Record their starting balances as owner-attributed unsolicited surplus, never F or solver spending authority. Verify that funding increased each balance by exactly F. This prevents pre-funding a predictable ATA from blocking an owner indefinitely. Reject any pre-existing account with a delegate, close authority, wrong mint/authority or unsupported state. Per-vault total balances, including surplus, are u64; separate surplus is never used in bounded valuation arithmetic.
- Owner pays all intent/vault rent in v1 and is the immutable rent beneficiary. No arbitrary rent receiver or sponsor account field. Owner-state rent remains deposited because the nonce state persists.

| From / instruction | Preconditions | Result |
|---|---|---|
| No intent / create_and_fund | correct owner signer; unused expected nonce; no active claim; unpaused funding; full valid immutable request | Funded, F booked, nonce incremented, claim counter +1 |
| Funded / settle_batch | all intents valid/funded/unexpired/unpaused; same policy; all guards and final deltas pass | Settled, booked claims paid to fixed recipients; donation claims retained |
| Funded / cancel | owner signer, exact intent; expiry irrelevant; pause/oracle irrelevant | Cancelled, no token transfer attempted |
| Cancelled / withdraw_asset | owner signer; exact vault/ATA; current balance accessible | all available balance of only that asset returned, its booked claim cleared atomically |
| Settled / withdraw_surplus | owner signer; exact vault/ATA | only post-settlement remaining donation balance returned |
| Settled or Cancelled / close_intent | all three vault balances zero; no booked claims; correct owner | close vaults and intent to owner, counter -1, clear active_intent |

Cancelled can never settle; Settled can never cancel or settle again. Withdraw on Funded is forbidden: cancel first. Expiry is not a state transition; settlement rejects `now >= expiry`, cancellation still works. Repeated cancel/settle/withdraw of an already consumed booked claim must not move booked value twice; an empty recovery returns a defined `NothingToWithdraw`, while later donations to still-open vaults may be recovered again. Closing only accounts with zero balances prevents erasing claims. After closure, ATA donations to a recreated old intent authority are outside any existing escrow claim: v1 MUST provide owner-authorized `recover_closed_vault` using persistent owner state and `nonce < next_nonce`, exact old PDA/ATA and owner recipient, without recreating an intent or changing nonce. This recovery can never authorize settlement or count as funding. It requires no config pause/oracle/solver and returns all donations plus recovered vault rent to owner. For this closed-vault recovery only, the supplied mint need not remain in the current config allowlist: validate the legacy SPL mint/program and derive both vault and owner recipient from it. This permits recovery of an old asset after a zero-claims policy rotation and confers no new settlement authority. Reject token-account delegates/close authorities and unsupported token programs as usual. Because original intent funding is impossible at an old nonce, no live booked claim can be stolen by this path; require active_intent != derived old PDA.

Cancellation wins only if executed first. Solana writable-account locks serialize cancel/settle; a transaction failure rolls back state and token movement but not network fees. Client reloads after a conflict. Owner refunds require owner signature and token transfer availability; a missing owner ATA is recreated at the exact same address, with owner paying devnet rent. Recover one asset per transaction so a failing/paused asset cannot stop recovery of others. Admin/solver are never recovery signers.

## Settlement instruction boundary

Input: 1–3 sorted unique intent addresses (one only for labelled technical probes; product acceptance requires at least two), expected snapshot sequence, up to six explicit stock/cash internal crosses and up to two typed external residual records. There are **no free debit, credit or allocation-weight arrays**. Each internal cross binds seller, buyer, stock, raw stock quantity and raw cash amount. Each residual binds stock/direction, minimum actual output and every owner's exact input contribution. settlement-accounting.md defines record widths/order, price bands, deterministic pro-rata external outputs and exact D/C/O derivation. Amounts are bounded, all owners/stock indices refer to the validated batch/config, and all internal/external stock and cash legs must reconcile actual transfers.

Stored mandate/config supplies identities and output bounds. Solver may submit; it cannot sign for vaults, choose recipients, alter bounds, inject a cash subsidy or carry owner keys. No new owner signature is required at settlement. A configured operational submitter confers no extra money authority; protocol fees remain zero. Settlement instruction body is schema u8=1, batch_count u8, expected_snapshot_sequence u64 LE, cross_count u8, each cross (19 bytes), residual_count u8, then each residual (stock_index u8, direction u8, minimum_output u64 LE, batch_count input amounts u64 LE each). With three owners/six crosses/two residuals it is **194 bytes**, excluding Anchor discriminator, account metas and transaction envelope. Runtime may reject fewer meaningful crosses under the no-round-trip rule; the serialized maximum remains bounded. Funding/canonical mandate sizes are unchanged by this settlement format.

Batch state PDA seeds `[b"batch", config_address]`; per-asset pool ATAs use this PDA authority. Always verify zero starting balances. Each pool starts and ends zero; unsolicited pool tokens cannot be treated as route proceeds. To avoid permanent donation DoS, an owner-independent permissionless `sweep_batch_surplus` may send pre-existing pool donations **only to config admin's canonical asset ATA** before settlement begins in a separate transaction, with no active execution. These are never intent funds: batch balances exist only transiently within one atomic transaction. This fixed destination is a disclosed donation sink, not a fee or solver revenue. Zero-start check must not be weakened to accommodate donations.

No arbitrary instruction bytes forwarded to CPI. Route input identifies only an admitted stock/cash direction, each owner's input contribution and minimum output. Exact route input is the checked sum of contributions; owner outputs follow measured proceeds pro rata, never caller-supplied weights. Program constructs the pinned adapter instruction from these and immutable policy identities. T10 freezes the concrete controlled-venue ABI; T16 implements the admitted residual integration and rejects any arbitrary program/account list. Residual routes cannot touch owner recipients/intent state or pass intent authority as signer. All checks/delta math follow settlement-accounting.md. The entire lifecycle and route behavior needs runtime tests before funding real demo escrows.

## Alias rules and remaining implementation gates

Reject duplicate owners/intents/mints/vaults/recipients within each role; reject role crossover among intent vaults, batch vaults, venue vaults, owner recipients, config/state and program accounts. V1 mints distinct; configured assets sorted; owners distinct; owner cannot be program/config/pool authority. Allowed repetition is explicitly limited to shared read-only program IDs/sysvars/config/mints, the same mint identity across several owners, owner signer = rent receiver, and an owner's funding source ATA = its later recipient ATA. Shared cash mint is expected; shared cash **token account** across owners is forbidden. Route input/output assets must differ; pool vaults must differ from every user/batch vault. Validate account owner/executable/status fields independently of address equality.

T04 gate: cross-language vectors + exact full transaction sizes with 3 owners/3 assets; include conservative reserved Pyth account/data/compute estimates separately labelled estimates. T14 gate: fixture oracle interface, timestamps/confidence/feed mapping, exact cross/external/value guards and numerical boundary vectors; it is a required dependency of T05 funding, which must not bypass fresh snapshot authentication. T15 conditional gate: exact authenticated Pyth update format, verifier ownership/instruction linkage, native feed/underlying-time/confidence/exponent conversion vectors. Until T15 passes, oracle_mode=1 is rejected everywhere. T10 gate: controlled adapter ABI and fee/reserve commitment. T16 gate: admitted actual residual CPI, per-owner proceeds attribution and rollback/delta tests. G2 gate: independent code review of all money paths. These gates do not weaken the v1 canonical contract.

## Reproducing the encoding evidence

Run `python3 docs/spec/check-wire-vectors.py` from a checkout. It regenerates expected fixtures in memory and compares them to wire-vectors.json; `--write` deliberately regenerates that file after a reviewed schema change. Positive encode/decode and object-key-order equality, 35 single-field-byte hash mutations, 15 invalid structured inputs, four malformed byte encodings and external pro-rata allocation and internal/external price-bound examples are covered. These tests are not independent security review, real ATA derivation checks or cross-language validation; T04 must add those. Policy preimage is 652 bytes. Encoding vectors deliberately use synthetic config/program/recipient identities; they are never transaction inputs.
