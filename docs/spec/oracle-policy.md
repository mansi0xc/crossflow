# T14 fixture reference implementation and integration boundary

Status: fixture guard/interface passed independent module review; T05/T09/T16 runtime wiring remains mandatory. This is **TEST PRICES**, a configured synthetic publisher, not Pyth or live equity data. Pyth mode 1 is rejected; T15 remains conditional. No new public program instruction or self-service oracle/config initializer exists in T14.

Rust oracle.rs implements the exact T02 integer policy, authenticates a snapshot's actual program owner, `["prices", config]` PDA, account discriminator/length, stored config/policy/publisher and requested sequence, and returns a VerifiedPrices object whose price fields cannot be fabricated outside the module. Methods enforce funding-reference equality, deposit-reference movement, per-cross band, per-owner external fill band, aggregate external band and final owner value loss. Checked u128 products and amount/price/decimal caps match the approved specification. `validate_snapshot` is the pure policy layer; runtime callers must use `read_fixture`.

Snapshot observations explicitly store exponent -6 (millionths of a test USD), absolute confidence interpretation 0, underlying time, publication time and market-closed state for each asset. Other exponents/confidence interpretations reject. Cash is exactly 1,000,000 with zero confidence; all three entries obey freshness. Publication wrapper freshness cannot refresh an old stock observation. Default limits remain age60 seconds, future2 seconds, confidence100bps, reference movement500bps, cross100bps, external200bps, total loss200bps. All equality boundaries are inclusive except intent expiry, handled by lifecycle code. Negative clocks and overflow reject.

`publish_fixture` takes actual runtime AccountInfo objects, requires `is_signer` for the configured publisher and the existing correct writable snapshot PDA/owner, and validates before copying serialized replacement bytes. Sequence must advance by exactly one with checked u64 addition; neither timestamp may regress for any feed. Publication validates structural/source/time/price rules but permits market_closed=true so the publisher can announce closure. Funding/settlement reads then reject MarketClosed; a subsequent authorized fresh update can reopen the market. A stale existing snapshot can be refreshed if the new observation is fresh and non-regressing. Initial snapshot helper uses sequence1 and verifies data; it allocates nothing and chooses no admin/publisher. Initialization must be invoked only inside T05's compiled manifest-bound configuration path.

## Required T05/T09 call-site wiring

`OracleBinding` is trusted program-internal input, not an instruction payload. T05 must construct it from its authenticated canonical config account after validating deployment/PDA/version/full policy hash and the compiled initializer contract in deployment-manifest.md. It contains config pubkey, policy hash, fixture publisher, the nine policy fields, and three configured mint/feed/decimals entries. T14 cannot authenticate a future config layout by itself; no caller-supplied binding may reach these helpers in a public instruction.

T05 must allocate the canonical fixture PDA with FixtureSnapshot::SPACE, initialize via initial_snapshot only under the reviewed initializer, and expose publication through a handler that obtains OracleBinding from that same validated config and Clock::get().unix_timestamp. Config initialization must not let an arbitrary first caller choose policy or publisher. Funding calls read_fixture with the body-approved policy hash and reviewed snapshot sequence, then check_funding_reference before transferring any tokens. Funding payload has no separate sequence field in T02: derive the selected sequence from the validated current account, while exact body funding-reference prices bind the approved values.

T09 settlement calls read_fixture with the stored mandate policy and request's expected_snapshot_sequence, checks reference movement for each funded mandate, calls check_cross on each explicit cross, and calls check_value_loss on derived owner outputs. T16 calls check_external_fill on every allocated nonzero participant and check_external_total on the measured complete leg. No display-only validation is sufficient. Runtime wrong-signer/owner/PDA/config and rollback integration tests belong to those binding tasks; these are tracked dependencies, not claimed complete here.

T07 implements an explicitly authorized config-update path. A policy update requires the registered admin signature, expected current version, exactly the next version, zero outstanding claim intents, and the new configured fixture publisher's signature. Deployment genesis, program and config identity stay fixed. The instruction validates the new policy and three fresh synthetic observations, then atomically replaces the policy commitment and reinitializes the canonical snapshot to sequence 1 under the new binding. A failed validation rolls back both changes. The old snapshot cannot be published against the new policy, and an intent cannot be funded across the update boundary. Admin rotation separately requires the current admin and expected version; pause flags can block funding or settlement but do not block cancellation or each asset's owner withdrawal. This is local-validator synthetic-price behavior; it does not authenticate Pyth or claim live equities.

## TypeScript mirror and evidence

policy.ts resolves exact canonical policy bytes/hash through @crossflow/contracts source, mirrors integer checks using bigint, and freezes verified price inputs. fixture.ts produces clearly labelled **unsigned proposals**. A matching publisher address in the client is not proof of a signature; only Rust's runtime signer/account checks enforce authority. Client code does not claim to authenticate RPC, token state, signatures or Pyth updates. JSON transport must use the existing strict decimal-string contract; these internal APIs take bigint and reject numeric price values.

Tests exercise shared T02 price vectors; exact and one-unit-outside price/time/confidence/value/reference boundaries; the $10/$11 subsidy counterexample; wrong feed/mode/publisher/sequence; unsupported exponent/confidence; stale underlying/fresh wrapper; closed market; zero/overflow inputs; and non-regressing updates. Rust also uses real AccountInfo data with the actual snapshot PDA/owner/discriminator to check unsigned publication refusal, failed-update byte preservation and valid publication. These host tests are not a validator execution or deployment.

No change to the 652-byte policy, 605-byte mandate or177-byte funding body. Snapshot account size is independently asserted by Rust serialization. Full oracle+route transaction capacity and compute remain downstream measured gates.
